# Online Store

![CI](https://github.com/ViniciuscLemos/online-store/actions/workflows/ci.yml/badge.svg)

A full e-commerce with Stripe payments, user accounts with permissions (customer and admin) and emails.

It's the biggest project in my portfolio so far, and I'm building it in stages. This README gets updated as each part is done.

## Progress

- [x] **Stage 1:** structure, database, sign up, login and permissions
- [ ] **Stage 2:** emails (account confirmation and password reset)
- [ ] **Stage 3:** products, stock and admin panel
- [ ] **Stage 4:** cart, orders and Stripe payments
- [ ] **Stage 5:** React front end
- [ ] **Stage 6:** deploy

## Tech

- **API:** Node.js, Express 5 and TypeScript
- **Database:** PostgreSQL with Drizzle ORM and SQL migrations
- **Validation:** Zod
- **Tests:** Vitest + Supertest, running on an in-memory Postgres (PGlite)

## Running

You need Node 22 or newer.

```bash
git clone https://github.com/ViniciuscLemos/online-store
cd online-store
npm install
npm run dev
```

The API runs at http://localhost:3333.

You don't need to install any database: without the `DATABASE_URL` variable, the API uses [PGlite](https://pglite.dev), which is Postgres compiled to run inside Node, and saves the data in the `server/.pglite` folder. To use a real Postgres:

```bash
docker compose up -d
cp server/.env.example server/.env   # and uncomment DATABASE_URL
npm run dev
```

Migrations run on their own when the API starts.

### Creating an admin

Sign up a normal account and then promote it:

```bash
npm run make-admin -w server -- your@email.com
```

With PGlite, stop the API before running this command, because it only lets one process use the database folder at a time.

### Tests

```bash
npm test
```

Each test file starts its own in-memory Postgres and applies the migrations, so the tests run real SQL, with no database mocks and no Docker. On GitHub Actions there's a second job that starts the API with a normal PostgreSQL to make sure it works there too.

## Routes

```
POST   /api/auth/register             creates the account and logs in
POST   /api/auth/login                logs in
POST   /api/auth/logout               logs out and ends the session
GET    /api/auth/me                   logged in user
GET    /api/admin/users               lists the users (admin only)
PATCH  /api/admin/users/:id/role      changes someone's role (admin only)
```

## How authentication works

I thought a lot about this part, so here's the reason behind each choice.

**Session in the database instead of JWT.** When someone logs in, the API generates a random token and sends it in a cookie. The database only keeps the SHA-256 hash of that token. On each request the API looks up the session by the hash and brings the user along. I picked this over JWT because a session can really be ended: logout deletes the session on the server, and whoever copied the cookie before can't use it anymore. With JWT the token keeps working until it expires.

**Permissions apply right away.** Since the user's role (customer or admin) is read from the database on every request, when an admin is demoted they lose access on the next request, without waiting for a token to expire.

**The cookie.** It's `httpOnly`, so the page's JavaScript can't read the token, even if someone manages to inject a script. It's `SameSite=Lax`, so the browser doesn't send the cookie on a POST made by another site. And as a second barrier against CSRF, the API refuses requests that change data when the `Origin` header isn't the front end's.

**The session lasts 30 days and renews itself.** If less than half the time is left and the person uses the store, the session gets another 30 days. People who use it all the time don't need to keep logging in, and people who disappeared get logged out after a month.

**Passwords.** They're stored as bcrypt hashes. On login, the message is the same for a wrong password and for an email with no account. When the email doesn't exist, the API compares the password against a fake hash, so the response takes the same time and you can't find out who has an account by timing it. Login and sign up are also limited to 10 attempts every 15 minutes per IP.

## Structure

```
server/
  drizzle/           SQL migrations generated by drizzle-kit
  src/
    app.ts           builds the Express app (gets the database, which makes testing easier)
    server.ts        connects to the database, runs the migrations and starts the API
    config.ts        environment variables validated with Zod
    db/              schema and connection (Postgres or PGlite)
    auth/            sessions, middlewares and login routes
    admin/           admin only routes
    lib/             errors, password hashing and tokens
  test/              integration tests
```
